# Decision 004: Tag API

- Status: Accepted
- Date: 2026-08-29
- Owner: Design System Team

## Decision

The public tag selector is `ds-tag`, accepted as proposed in
[RFC 003](../rfcs/003-tag.md).

The initial API includes:

- `variant="neutral"` / `"success"` / `"error"` / `"warning"` / `"info"`
- `dismissible` (default `false`) with a `dismissLabel` input for the
  dismiss button's accessible name
- A `dismissed` output — the component signals removal intent, it does
  not remove itself

Two new semantic tokens were added as part of this decision:
`--ds-color-feedback-warning` (new primitive `color.yellow.500`,
`#f2b705`) and `--ds-color-feedback-info` (new primitive
`color.blue.500`, `#1967d2`). `success`/`error`/`neutral` reuse existing
tokens.

## Why

Status labels needed all five severities product teams actually use, not
just the two (`success`/`error`) that happened to already have tokens.
Cutting `warning`/`info` to avoid a token-pipeline change would have meant
picking the wrong reason to scope a component — see RFC 003's
Alternatives for why reusing an existing token for a different severity
was rejected instead.

The dismiss button is optional (`dismissible` default `false`) because
most tag usage is a read-only status label; making every tag interactive
would add unwanted keyboard stops. It emits rather than self-removes,
keeping list ownership with the consumer, consistent with `ds-input`'s
validation model.

## Consequences

Changing the selector, removing a `variant` value, or removing
`dismissible`/`dismissLabel`/`dismissed` after the first public release is
a breaking change.

`--ds-color-feedback-warning` and `--ds-color-feedback-info` are now part
of the public token surface (available via `list_tokens` and consumed by
any future component) — removing or repurposing them is also a breaking
change, not just a `ds-tag` concern.
