# RFC: Card

- Status: Proposed
- Author: Alexandra
- Date: 2026-08-29
- Reviewers: Pending

## Problem

Product surfaces (dashboards, lists, settings pages) repeatedly build the
same grouped-content container by hand: a bordered or shaded box with
consistent padding and corner radius. Without a shared component, that
padding, radius, and surface color drift between applications the same way
button and input styling did before `ds-button` and `ds-input` existed.

The first release is a plain content container. It does not attempt to
solve header/body/footer layout, elevation/shadow, or clickable
("navigation") cards — those are separate concerns with their own
accessibility implications and are deferred to keep this API focused, the
same way `ds-input` deferred number/date entry and interactive icons.

## Proposed API

The component selector is `ds-card`.

```html
<ds-card>
  <h3>Plan usage</h3>
  <p>You've used 8 of 10 seats this month.</p>
</ds-card>

<ds-card variant="subtle" padding="lg">
  <p>Quieter surface, more breathing room.</p>
</ds-card>
```

### Inputs

| Input | Type | Default | Description |
|---|---|---|---|
| `variant` | `default`, `subtle` | `default` | Background/border treatment |
| `padding` | `sm`, `md`, `lg` | `md` | Internal spacing |

There is no `elevated`/shadow option in this release — see Open questions.

### Content

A single default content projection (`<ng-content>`). No named header/body/
footer slots in v1.

## Alternatives

- Utility CSS classes applied directly by consumers: rejected for the same
  reason application-specific inputs were rejected in the `ds-input` RFC —
  it duplicates a visual decision (padding/radius/surface pairing) that
  should live in one place.
- A composite `ds-card` with `ds-card-header` / `ds-card-footer` child
  components: deferred. Real usage should tell us whether consumers need
  structured slots or whether plain content projection plus normal
  heading markup is enough.
- A clickable/navigable card variant (wrapping an `<a>` or emitting a click
  event): rejected for v1 — a card that's also a link has real accessible-
  name and nested-interactive-content implications that deserve their own
  RFC rather than being bolted onto a plain container.

## Accessibility

- Renders as a plain `<div>` with no implicit ARIA role. A card is a
  visual grouping, not a landmark by default — adding `role="region"` or
  a forced accessible name for every card would create screen-reader
  landmark noise on pages with many cards.
- Consumers are responsible for a heading (`<h2>`–`<h6>`) inside the card
  when its content needs a name/landmark; the component does not
  prescribe heading level, since that depends on the surrounding page
  structure.
- No focus behavior in v1: the card itself is never a keyboard-focus
  target. If a future clickable-card variant is proposed, that RFC must
  cover focus and accessible-name requirements at that point.

## Design tokens

Uses only existing semantic tokens — no new tokens needed:

- `--ds-color-surface-default` / `--ds-color-surface-subtle` for `variant`
- `--ds-color-border-default` for the border
- `--ds-radius-lg` for the corner radius (matching `ds-button`)
- `--ds-space-3` / `--ds-space-4` / `--ds-space-6` for `padding="sm"` /
  `"md"` / `"lg"`

## Versioning impact

New public component: minor release, e.g. `0.1.0` to `0.2.0`. Not major,
since it adds to the public API without changing anything existing.

## Adoption and migration

Consumers discover `ds-card` the same way as existing components:

- Package public API and generated type declarations
- Storybook stories and autogenerated (compodoc) documentation
- `docs/components/card.md`
- The MCP server's `list_components` / `get_component_api` tools — unlike
  the `ds-input` RFC, MCP-based discovery is no longer deferred; it's a
  working part of the AI-readiness surface and should list `ds-card` from
  day one via `component-registry.json`.

No migration path is required — there is no existing design-system card to
replace.

## Open questions

- Should there be an `elevated` (shadow) variant? Resolved for v1: no —
  there are no shadow/elevation tokens in the token pipeline yet
  (`tokens/primitives.tokens.json` has no shadow primitives). Adding one
  primitive value just for this component would violate the "no
  component-specific primitive values" rule from the `ds-input` RFC.
  Revisit once elevation tokens exist as their own token-pipeline change.
- Should `ds-card` support `variant="inverse"` (dark surface)? Deferred —
  no confirmed use case yet; `--ds-color-surface-inverse` exists as a
  token if this comes up later.
- Header/footer slots — deferred, see Alternatives.
