# RFC: Tag

- Status: Proposed
- Author: Alexandra
- Date: 2026-08-29
- Reviewers: Pending

## Problem

Lists and cards (including `ds-card`) need a small inline label to show
status or category — "Active", "Beta", "Failed" — without every consuming
team inventing their own pill-shaped `<span>` with hand-picked colors.
That's the same drift `ds-button`, `ds-input`, and `ds-card` exist to
prevent, just for status labels instead of controls or containers.

## Proposed API

The component selector is `ds-tag`.

```html
<ds-tag>Beta</ds-tag>
<ds-tag variant="success">Active</ds-tag>
<ds-tag variant="error">Failed</ds-tag>
<ds-tag variant="warning">Pending review</ds-tag>
<ds-tag variant="info">New</ds-tag>

<ds-tag
  variant="info"
  [dismissible]="true"
  dismissLabel="Remove filter: Beta"
  (dismissed)="removeFilter('beta')"
>
  Beta
</ds-tag>
```

### Inputs

| Input | Type | Default | Description |
|---|---|---|---|
| `variant` | `neutral`, `success`, `error`, `warning`, `info` | `neutral` | Status color |
| `dismissible` | `boolean` | `false` | Shows a dismiss button |
| `dismissLabel` | `string` | `'Remove tag'` | Accessible name for the dismiss button |

### Output

| Output | Payload | Description |
|---|---|---|
| `dismissed` | `void` | Emitted when the dismiss button is activated |

The component does not remove itself from the DOM. It signals intent —
the consumer owns removing it from whatever list/model produced it, the
same division of responsibility `ds-input` uses for validation: the
component presents state, the application owns the data.

### Content

A single default content projection (text label).

## Alternatives

- A `warning`/`info` variant without new tokens, reusing an existing
  color: rejected — reusing `feedback-error` for warning, for example,
  would make two different severities visually identical. The correct fix
  is the token-pipeline change this RFC includes (two new primitives, two
  new semantic aliases), not a workaround in the component.
- Baking dismiss behavior into every tag unconditionally: rejected —
  most tag usage (status labels on a card, category chips in read-only
  content) has no reason to be removable, and forcing a button into every
  instance adds keyboard stops and DOM nobody asked for. `dismissible`
  defaults to `false`.
- The dismiss button building the removal into the component itself
  (e.g. the tag deletes itself from an internal list): rejected — this
  component doesn't own a list, the consumer does. Emitting `dismissed`
  and letting the consumer decide matches how every other stateful
  decision in this library works.
- An icon slot (separate from the dismiss button): deferred, no confirmed
  use case yet.

## Accessibility

- The tag root renders as a plain `<span>`, non-interactive, no ARIA role,
  no keyboard focus target.
- When `dismissible` is `true`, a real `<button type="button">` is
  rendered inside the tag. Being a real button gives it focus and
  Enter/Space activation for free — no custom keyboard handling needed.
- The dismiss button's accessible name comes from `dismissLabel`, not the
  tag's projected content — the component cannot read projected text as a
  string, so a generic default (`'Remove tag'`) is provided, and consumers
  should override it with something specific ("Remove filter: Beta")
  whenever more than one dismissible tag can appear together, so screen
  reader users can tell them apart.
- Status is conveyed by the tag's **text content**, not color alone —
  `variant` reinforces the text, it never replaces it. Same rule as
  `ds-button`'s "button text must describe the action."

## Design tokens

Requires a token-pipeline change alongside this component:

- New primitives: `color.yellow.500` (`#f2b705`), `color.blue.500`
  (`#1967d2`)
- New semantic aliases: `color.feedback.warning` → `color.yellow.500`,
  `color.feedback.info` → `color.blue.500`

No new tokens needed for `success`/`error`/`neutral` — they reuse existing
`--ds-color-feedback-success`, `--ds-color-feedback-error`, and
`--ds-color-surface-subtle` respectively.

Foreground pairing (no new "-text" tokens needed, existing ones cover it):

| Variant | Background | Text |
|---|---|---|
| `neutral` | `--ds-color-surface-subtle` | `--ds-color-text-default` |
| `success` | `--ds-color-feedback-success` | `--ds-color-text-inverse` |
| `error` | `--ds-color-feedback-error` | `--ds-color-text-inverse` |
| `warning` | `--ds-color-feedback-warning` *(new)* | `--ds-color-text-default` |
| `info` | `--ds-color-feedback-info` *(new)* | `--ds-color-text-inverse` |

Padding/radius: `--ds-space-1` / `--ds-space-2`, `--ds-radius-sm`.

## Versioning impact

New public component plus two new semantic tokens: minor release. Not
major — nothing existing changes, this is purely additive to both the
component set and the token surface.

## Adoption and migration

Same discovery path as `ds-card`: public API, Storybook, `docs/components/
tag.md`, and the MCP server (`component-registry.json` entry, and
`list_tokens` now also returns the two new feedback tokens). No migration
path — no existing design-system tag to replace.

## Open questions

- None open — icon slot was the only deferred item and has no confirmed
  use case yet.
